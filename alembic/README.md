# Alembic Migrations Directory

This directory contains the database migration environment for the **Task Management REST API**, powered by **Alembic** and **SQLAlchemy 2.0**.

Alembic provides programmatic, version-controlled schema evolution for PostgreSQL. Instead of running ad-hoc SQL scripts or dropping and recreating databases, migrations allow the schema to evolve safely and predictably across development, testing, staging, and production environments.

---

## 1. Directory Structure

```text
alembic/
├── env.py              # Migration execution environment script
├── script.py.mako      # Mako template used to generate new migration files
├── versions/           # Version-controlled migration revisions
│   ├── *_*.py          # Immutable migration script
│   └── README.md       # Documentation for migration revisions

```

## 2. Key Components & How It Works

### [`alembic/env.py`](env.py)
The core Python script invoked by Alembic CLI commands (`alembic revision`, `alembic upgrade`, etc.).

1. **Dynamic Database Configuration:**
   Instead of hardcoding database credentials inside `alembic.ini`, `env.py` dynamically reads the connection URL from the application settings:
   ```python
   from app.core.config import settings

   config.set_main_option("sqlalchemy.url", settings.DATABASE_URL)
   ```
   This honors the 12-Factor App methodology and prevents credential leakage.

2. **Model Autogeneration Discovery:**
   `env.py` registers the SQLAlchemy declarative metadata:
   ```python
   import app.models  # Ensures all ORM models are imported and registered
   from app.core.database import Base

   target_metadata = Base.metadata
   ```
   When `--autogenerate` is passed, Alembic compares `target_metadata` against the actual PostgreSQL database schema to detect created, modified, or dropped tables, columns, indexes, and constraints.

3. **Offline vs. Online Migration Modes:**
   - **`run_migrations_online()`:** Connects directly to the PostgreSQL database via SQLAlchemy engine to apply transactional DDL changes.
   - **`run_migrations_offline()`:** Generates raw SQL scripts without an active database connection (useful for review or air-gapped database environments).

## 3. Common Alembic Commands

All commands should be executed from the project root with the virtual environment activated:

| Command | Description |
| :--- | :--- |
| `alembic current` | Display the current database revision applied to PostgreSQL. |
| `alembic heads` | Show the latest available migration revision(s) in the repository. |
| `alembic history --verbose` | Show the chronological history of all migration revisions. |
| `alembic upgrade head` | Apply all pending migrations up to the latest revision. |
| `alembic downgrade -1` | Roll back the most recently applied migration by one revision. |
| `alembic revision --autogenerate -m "message"` | Detect model changes and generate a new migration revision file. |

## 4. Migration Best Practices

1. **Always Inspect Autogenerated Files:**
   Alembic autogenerate is powerful, but it does not detect everything (e.g., table renames appear as drop + create). Always review the generated script in `alembic/versions/` before running `upgrade`.
2. **Never Edit an Applied Migration:**
   Once a migration has been applied to any shared environment or committed to main, treat it as immutable. To make changes, generate a new forward revision.
3. **Keep `upgrade()` and `downgrade()` Symmetrical:**
   Every schema modification in `upgrade()` must have an inverse operation in `downgrade()` to guarantee safe rollback capabilities.
